# 雍和宫许愿法则：跨域精确指令框架

> **一句话核心**：愿望一定会实现——除非你把每一个细节、边界和排除条件都说清楚，否则它将以你最不想要的方式实现。

## 模块1：核心法则——许愿反噬原理 ★

> **source**: 小红书视频"去雍和宫许愿指令一定要清晰明确"评论区真实案例

### 法则陈述

> **任何指令（愿望、目标、请求、prompt）都会被执行。但执行者（神灵、命运、AI、下属、法律系统）只执行你字面上说的，不执行你心里想的。你省略的每一个细节，都会被以对你最不利的方式填补。**

这不是迷信，这是信息论的基本原理：接收方只能根据接收到的信息行动，发送方脑中未编码传输的意图，对执行过程没有任何约束力。

### 猴爪效应的现实映射

"猴爪效应"（The Monkey's Paw）：一个能实现愿望的神奇物品，但每个愿望都以扭曲的方式实现，带来灾难性后果。这并非超自然现象，而是**模糊指令在无约束执行下的必然结果**。

### 评论区真实案例库

以下案例全部来自视频评论区，是"模糊指令反噬"的活教材：

| 案例 | 模糊指令 | 字面执行结果 | 缺失了什么 |
|------|---------|------------|-----------|
| **减肥愿望** | "瘦十斤" | 第二天食物中毒上吐下泻，确实瘦了 | 没说"通过健康的方式""不伤害身体" |
| **发财愿望** | "发财" | 当年得重疾，重疾险赔了一笔钱 | 没说"通过正当收入""不以健康为代价" |
| **正缘愿望** | "遇到正缘" | 回家一周后分手了（确实"遇到"了正缘不存在这件事） | 没说"维持长期关系""对方也喜欢我" |
| **发财（小额）** | "发点小财" | 弟弟当天发了300元红包 | 没说"金额要大""不是来自亲友" |
| **治病愿望** | "习惯性崴脚能好" | 从楼梯上滚下来更严重了，后来买护踝好了 | 没说"不要通过更严重的伤害来治愈" |
| **遗产愿望** ★ | "不出钱或少出钱换到我现在住的房子" | 两周后原样实现：给另一个继承人3万多，全部了结，完成房产过户 | **这个愿望很精确！指定了金额范围、具体房产、交换方式** |

### 唯一的成功案例

遗产案例是评论区中**唯一完全按照愿望者意图实现**的案例。原因：许愿者明确指定了：
1. **具体目标**：换到现在住的房子
2. **金额约束**：不出钱或出少一点
3. **时间预期**：赶紧了结
4. **结果形式**：房产过户

### 反噬的三种机制

| 机制 | 原理 | 现实映射 |
|------|------|---------|
| **字面执行** | 执行者只对字面意思负责，不对隐含意图负责 | AI只执行prompt字面意思；法律只看合同字面条款 |
| **最省力路径** | 宇宙/AI/人倾向于以最低成本满足字面条件 | 瘦十斤→食物中毒（比运动省力）；发财→保险赔付（比创业省力） |
| **资源置换** | 实现A必须消耗B，但你没说不能消耗B | 发财=消耗健康；正缘=消耗现有关系 |

### 精确指令 vs 模糊指令的本质区别

```
模糊指令："我想要X"
  → 执行者自由选择实现路径 → 路径可能经过你不想要的地方

精确指令："我想要X，通过Y方式实现，不要Z，在W时间内，且不消耗V"
  → 执行者的自由度被约束 → 实现路径被限制在可接受范围内
```

### 可执行步骤

1. **写下你的愿望/指令/目标的原始版本**：先不管精确性，写下来
2. **找缺失**：对照"精确指令五要素"（模块2），找出你省略了哪些要素
3. **补约束**：为每个缺失要素添加明确的约束条件
4. **红队测试**：假装你是最恶意的执行者，想方设法用字面意思实现这个指令但给你最差的结果
5. **修补漏洞**：针对红队测试发现的漏洞，添加排除条件

## 模块2：AI提示词精确性 ★

> 当你的AI输出跑偏了，问题不在AI，在你的prompt。

### 核心原则

> **AI是终极的"字面执行者"。它不会猜测你的意图，不会填补你的省略，不会自动加上你以为理所当然的约束。你写的每一个词就是它拥有的全部信息。**

### Prompt精确性检查清单

| 维度 | 模糊（会跑偏） | 精确（不会跑偏） |
|------|-------------|----------------|
| **角色** | "帮我写个东西" | "你是XX领域的专家，帮受众Y解决Z问题" |
| **任务** | "写得好一点" | "将以下文本的语气从学术改为科普，保持核心论点不变，目标读者是本科生" |
| **格式** | "给我个结果" | "输出格式：1.摘要（100字内）2.正文 3.参考资料，用Markdown" |
| **约束** | "随便写" | "不要使用'然而'作为段落开头；不要超过3个要点；不要编造引用" |
| **示例** | 无 | "参考这个风格：[示例文本]" |
| **排除** | 无 | "不要使用以下词汇：[列表]" |

### "愿望反噬"在AI中的映射

| 现实许愿反噬 | AI Prompt反噬 |
|------------|--------------|
| "瘦十斤"→食物中毒 | "帮我简短一点"→AI删掉了关键信息 |
| "发财"→保险赔付 | "帮我写得好一点"→AI用了华丽但空洞的辞藻 |
| "遇到正缘"→分手 | "帮我优化这段代码"→AI重构了但引入了bug |

### 黄金法则

> **好的prompt = 你希望一个完全不了解背景的优秀执行者，仅凭你写的这段话就能完成任务。**

如果你把prompt给一个陌生人，他能完成任务吗？如果不能，说明你的prompt太依赖"隐含上下文"了。

### 可执行步骤

1. **先写角色+任务+格式三要素**：缺少任何一个都会导致跑偏
2. **加排除条件**：明确说"不要做什么"比说"要做什么"更重要
3. **提供示例**：给AI看一个你想要的输出样本
4. **做红队测试**：问AI"你能不能用一个完全不同但字面满足我要求的方式来回答？"如果能，你的prompt有漏洞
5. **迭代修正**：如果AI第一次输出不满意，先改prompt再重新生成，不要在对话中修修补补

## 模块3：目标设定的精确性 ★

### SMART法则的深化理解

SMART目标设定框架与"指令精确性法则"高度一致：

| 要素 | 含义 | 许愿反噬映射 |
|------|------|------------|
| **S**pecific（具体） | 不是"发财"而是"月收入增加5000元" | "发财"→保险赔付 |
| **M**easurable（可衡量） | 有明确的完成标准 | "瘦十斤"有数字但仍缺约束 |
| **A**chievable（可达成） | 在现有条件下可行 | 避免设定不可能的目标导致走极端路径 |
| **R**elevant（相关） | 和你的真实需求相关 | "正缘"和"维持关系"是两件事 |
| **T**ime-bound（有时限） | 明确截止时间 | 避免"永远在实现的路上" |

### 被忽视的第六要素：排除条件（Exclusion）

SMART缺了一个关键维度：**你不想要什么**。

> 完整的精确目标 = SMART + Exclusion

```
目标："在6个月内（T），通过副业（E排除：不以健康为代价），
      使月收入增加5000元（S+M），利用我现有的编程技能（A+R）"
```

### 目标设定的"反噬检查法"

写下你的目标后，问自己三个问题：

1. **"如果我通过一种我不想要的方式实现了这个目标，会是什么方式？"**
   - 例如：目标是"升职"→反噬方式可能是"通过同事离职获得了空缺"
   
2. **"实现这个目标需要消耗什么资源？我接受吗？"**
   - 例如：目标是"发论文"→消耗的可能是"健康/关系/其他项目的时间"

3. **"如果目标完全字面化实现了，但我觉得不开心，可能是什么原因？"**
   - 例如：目标是"赚100万"→实现了但过程违法/损害了声誉

### 可执行步骤

1. **用SMART+E格式写目标**：每个要素都填上
2. **做反噬检查**：回答上面三个问题
3. **补排除条件**：把反噬检查发现的不想要路径写进排除条件
4. **设定检查点**：不是"6个月后看结果"，而是"每月检查一次是否走在了不想要的路径上"

## 模块4：法律文书的精确性 ★

### 核心原则

> **合同是给最坏情况准备的，不是给最好情况准备的。你省略的每一个条款，都会在纠纷时被对方利用。**

### 评论区映射

"审判长：原告请明确你的诉请" —— 这条评论深刻揭示了法律系统对精确性的要求。法官就像命运之神，只按你字面提出的诉请来判，不会替你补全。

### 合同/协议的精确性检查

| 维度 | 模糊条款（有漏洞） | 精确条款（无漏洞） |
|------|----------------|----------------|
| **金额** | "合理费用" | "不超过X元，超出部分需书面确认" |
| **时间** | "尽快完成" | "在YYYY年MM月DD日前完成，逾期按每日X%支付违约金" |
| **范围** | "相关服务" | "具体包括A、B、C，不包括D、E" |
| **标准** | "高质量" | "符合XX标准/规范，具体指标为..." |
| **变更** | "如有变更协商解决" | "变更需双方书面确认，口头变更无效" |
| **终止** | "任何一方可终止" | "提前30天书面通知，已完成的工作按XX结算" |

### "愿望反噬"在合同中的表现

| 许愿反噬 | 合同漏洞 |
|---------|---------|
| "瘦十斤"→食物中毒 | "尽快交付"→对方拖了半年也算"尽快" |
| "发财"→保险赔付 | "合理利润"→对方把所有成本算进去后利润为零 |
| "正缘"→分手 | "独家合作"→对方在关联公司用另一个品牌做同样的事 |

### 可执行步骤

1. **列举所有可能的最坏情况**：对方违约、延迟、质量不达标、单方终止
2. **为每种情况写明后果**：违约金、赔偿、终止条件
3. **定义所有模糊概念**："合理""尽快""高质量""相关"→用具体标准替代
4. **写排除条款**：明确什么不在范围内
5. **让别人挑刺**：找一个不站在你这边的聪明人，问他能不能钻空子

## 模块5：科学假设的精确性 ★

### 核心原则

> **一个不可证伪的假设，就像一个永远"灵验"的许愿——它什么都能解释，因此什么都没解释。**

### 精确假设 vs 模糊假设

| 特征 | 模糊假设（不可证伪） | 精确假设（可证伪） |
|------|-------------------|------------------|
| 预测 | "X可能对Y有某种影响" | "X在浓度>10μM时使Y的表达量增加2倍以上(p<0.01)" |
| 边界 | 不说在什么条件下 | 明确适用范围和排除条件 |
| 证伪 | 无法被实验否定 | 明确什么结果会否定它 |
| 可操作 | 不知道做什么实验 | 实验设计和预期结果明确 |

### "愿望反噬"在科研中的映射

| 许愿反噬 | 科研陷阱 |
|---------|---------|
| 模糊愿望→字面实现但结果惨 | 模糊假设→p-hacking出"显著"但不可重复的结果 |
| "发财"→通过生病实现 | "有效"→通过不合理的对照组实现 |
| 没说排除条件→被反噬 | 没说排除混杂因素→得到虚假关联 |

### 波普尔可证伪性的实践

好的假设必须明确回答："什么实验结果能证明我是错的？"

如果你说不出来，你的假设就是模糊的——就像你说"我想发财"但没说不能通过什么方式。

### 可执行步骤

1. **写出假设的精确版本**：包括变量、方向、幅度、条件
2. **定义证伪条件**：什么结果会否定这个假设？
3. **列举混杂因素**：什么其他因素可能导致相同结果？
4. **设对照组**：确保对照组能排除替代解释
5. **预注册**：在做实验前就写好分析方案，避免事后调整标准

## 模块6：项目需求的精确性 ★

### 核心原则

> **需求文档就是你给开发团队的"许愿"。模糊的需求 = 团队会用最省力的方式实现字面意思。**

### 需求精确性检查清单

| 维度 | 模糊需求 | 精确需求 |
|------|---------|---------|
| **功能** | "用户管理" | "管理员可以增删改查用户，普通用户只能查看自己的信息" |
| **性能** | "响应快" | "API响应时间P99<200ms，并发1000" |
| **体验** | "界面好看" | "参考XX网站的设计风格，主色调为蓝色系" |
| **范围** | "做好登录功能" | "包括：邮箱/手机注册、密码登录、第三方OAuth、忘记密码。不包括：SSO、生物识别" |
| **验收** | "能用就行" | "验收标准：能完成注册→登录→退出全流程，覆盖Chrome/Safari/Firefox" |

### "愿望反噬"在项目管理中的映射

| 许愿反噬 | 需求反噬 |
|---------|---------|
| "瘦十斤"→食物中毒 | "做得简洁一点"→删掉了关键功能 |
| "发财"→保险赔付 | "功能丰富一点"→加了一堆没人用的功能，工期翻倍 |
| 没说排除条件 | 没说"不包括XX"→团队做了你不需要的东西 |

### 可执行步骤

1. **用用户故事+验收标准写需求**："作为X角色，我想要Y功能，以便Z目的。验收标准：..."
2. **写排除清单**：明确说"本期不做什么"
3. **定义验收标准**：每个需求都要有可测试的完成标准
4. **做需求评审**：让开发人员复述他们理解的需求，对比和你的理解是否一致
5. **用原型验证**：先做低保真原型确认方向，再做详细需求

## 模块7：沟通与谈判的精确性 ★

### 核心原则

> **沟通中最大的误解来源不是"说错了"，而是"以为对方知道了你没说的"。**

### "信息不对称"的许愿映射

评论区中的许愿者和"命运"之间就是最极端的信息不对称：你心里有完整意图，但命运只听到了你嘴上说出的那几个字。

在沟通中同样如此：
- 你以为"这还用说吗？"
- 对方以为"你没说，所以我按我的理解来"

### 精确沟通的三个层次

| 层次 | 原则 | 操作 |
|------|------|------|
| **1. 说出来** | 不要假设对方知道 | 把所有"理所当然"的前提明确说出来 |
| **2. 确认理解** | 不要假设对方理解了 | 让对方复述他的理解 |
| **3. 写下来** | 不要依赖记忆 | 口头沟通后邮件确认要点 |

### 谈判中的精确性

在谈判中，模糊的条款就是给对方留的"后门"：

- "原则上同意" = "我不同意但不想现在说"
- "后续再讨论" = "我永远不会主动提"
- "尽量满足" = "我不保证能做到"
- "特殊情况除外" = "所有情况都是特殊情况"

### 可执行步骤

1. **用"我的意思是X，不是Y"的句式**：主动澄清可能的误解
2. **让对方复述**："为了确保我们理解一致，你能说一下你听到了什么吗？"
3. **邮件确认**：口头沟通后发邮件"总结今天讨论的要点"
4. **对模糊回应追问**：当对方说"尽量"时，问"如果做不到怎么办？"
5. **写排除项**："我要的是A，不是B，也不是C"

## 模块8：精确指令速查清单 ★

### 精确指令五要素（FLASH）

| 要素 | 含义 | 检查问题 | 反噬案例 |
|------|------|---------|---------|
| **F**ormat（格式） | 你想要什么形式的输出 | 你期望的结果长什么样？ | "帮我做个方案"→做成了PPT你要的是文档 |
| **L**imit（边界） | 做什么和不做什么 | 有什么是明确不要的？ | "优化代码"→重构了但改了业务逻辑 |
| **A**udience（受众） | 给谁看的 | 最终使用者/接收者是谁？ | "写篇介绍"→写成技术文档客户看不懂 |
| **S**tandard（标准） | 怎么算完成 | 验收标准是什么？ | "写得专业一点"→加了术语但没解决核心问题 |
| **H**ole（漏洞） | 红队测试 | 恶意执行者怎么钻空子？ | "简短一点"→删了关键信息 |

### 30秒精确指令自检法

写下你的指令/目标/prompt后，花30秒回答：

1. **如果我只看字面意思，能不能用一种我不想要的方式实现？** → 如果能，加排除条件
2. **我有没有说"不要怎样"？** → 如果没有，加上
3. **我有没有说"做到什么程度算完成"？** → 如果没有，加上
4. **如果给一个不了解背景的陌生人，他能执行吗？** → 如果不能，补上下文

## 模块9：高级主题——精确性的边界 ★

### 过度精确的陷阱

精确不是越多越好。过度精确会导致：

| 陷阱 | 表现 | 后果 |
|------|------|------|
| **规格冻结** | 需求写得过于详细，无法适应变化 | 环境变了但需求不变，做出来的东西过时 |
| **分析瘫痪** | 花太多时间定义精确性 | 永远无法开始执行 |
| **创造力扼杀** | 每一步都规定死 | 执行者没有空间发挥更好的方案 |

### 精确性的"70%法则"

> **在70%的确定性水平上开始执行，在执行中修正剩余30%。**

完全精确是不可能的（就像你不可能预见雍和宫许愿的所有反噬路径）。但你可以做到：
1. **关键维度精确**：最重要的3-5个约束必须精确
2. **次要维度灵活**：允许执行者有一定自由度
3. **检查点修正**：在执行过程中设置检查点，发现偏移及时修正

### 精确度分层

| 层次 | 适合精确 | 适合灵活 |
|------|---------|---------|
| **目标层** | 最终要达到什么结果 ★ | |
| **约束层** | 不能触碰什么底线 ★ | |
| **方法层** | | 可以用多种方式实现 |
| **细节层** | | 具体执行可以灵活 |
| **迭代层** | | 根据反馈调整 |

### 可执行步骤

1. **区分关键维度和次要维度**：不是所有东西都需要同等精确
2. **对关键维度做反噬检查**：确保核心目标不会被字面化扭曲
3. **对次要维度留出灵活空间**：允许执行者用更好的方式实现
4. **设置检查点**：在30%、60%、90%进度时检查是否偏航
5. **接受不完全精确**：目标是"足够精确不被反噬"，不是"完美精确毫无歧义"
